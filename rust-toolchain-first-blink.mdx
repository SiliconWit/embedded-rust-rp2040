A first program in a new language on a new chip often costs a day before any LED lights: the compiler builds for the wrong processor, the linker does not know where the chip's memory is, and nothing reaches the board. This lesson removes that day. You install the Rust tools, create a project for the RP2040 (the microcontroller on the Raspberry Pi Pico), and load a program that blinks an LED and prints log lines in your terminal. You also meet the first Rust rule that surprises a C programmer: a pin is a value, and only one part of the program can hold it. Every later project in the course uses the same files and commands. #EmbeddedRust #RP2040 #Toolchain

## What We Are Building

<Card title="Blinking LED with defmt RTT Logging" icon="star">
An LED that blinks once per second (1 Hz) on the Raspberry Pi Pico. Each time the LED changes, the program prints its state and a cycle counter in your terminal. The log lines travel through the debug probe by RTT (Real-Time Transfer: the probe reads a small buffer in the chip's RAM, so no UART pin is used). The logging library is called defmt. When the LED blinks and the lines appear, every tool in the chain works.
</Card>

A debug probe is a small adapter between your computer and the chip. It loads the program and reads the log lines through SWD (Serial Wire Debug), a port of two signal wires on the bottom edge of the Pico: SWCLK (clock) and SWDIO (data), plus GND. A second Pico with the Picoprobe firmware works as a probe.

## Installing the Rust Toolchain

<InArticleAd />

Your computer and the RP2040 have different processors: the RP2040 has an ARM Cortex-M0+ core. So the compiler must cross-compile, which means it runs on one processor and produces code for another. You install the compiler, a target (the description of the processor to build for), and a tool that speaks to the debug probe.

<Tabs>
<TabItem label="Linux (Ubuntu/Debian)">
```bash
# Install Rust via rustup
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
source $HOME/.cargo/env

# Add the Cortex-M0+ cross-compilation target
rustup target add thumbv6m-none-eabi

# Install probe-rs for flashing and RTT
cargo install probe-rs-tools
```

### Why Each Tool?

| Tool | Purpose |
|------|---------|
| `rustup` | Installs the Rust compiler and its targets, and keeps them up to date |
| `thumbv6m-none-eabi` | The target for ARM Cortex-M0+ (the RP2040 core). `none` means there is no operating system |
| `probe-rs` | Loads the program into flash through the probe, shows the RTT log lines, and serves the GDB debugger |
| `flip-link` | A linker wrapper that puts the stack at the bottom of RAM, so a stack overflow stops the program at once and cannot overwrite your variables |
| `elf2uf2-rs` | Converts the built program (an ELF file) to UF2 format for loading without a probe |

### Connecting the Debug Probe

If you use a second Pico as the probe, first load the [Picoprobe firmware](https://github.com/raspberrypi/picoprobe/releases) onto it: hold BOOTSEL, plug it in, and copy the UF2 file onto the drive that appears. Then join the three SWD pins, each to the pin of the same name:

```text
  Picoprobe / ST-Link        Target Pico
  (debug probe)              (bottom edge)
  ┌─────────┐                ┌─────────┐
  │  SWDIO  ├────────────────┤  SWDIO  │
  │  SWCLK  ├────────────────┤  SWCLK  │
  │   GND   ├────────────────┤   GND   │
  └─────────┘                └─────────┘
```

Test the connection:

```bash
probe-rs list
```

You should see your probe listed (e.g., `Picoprobe (CMSIS-DAP)` or `STLink V2`). Then test the target:

```bash
probe-rs info --chip RP2040
```

This should print the RP2040 memory layout and core information.

### Cargo.toml

Cargo is Rust's build tool. It does the work of `make`, CMake and a library downloader together. The file `Cargo.toml` lists the libraries the project needs, and Cargo fetches and compiles them. Rust calls a library a crate. Create a new project:

```bash
cargo init rp2040-blink
cd rp2040-blink
```

Replace the generated `Cargo.toml` with:

```toml
[package]
name = "rp2040-blink"
version = "0.1.0"
edition = "2021"

[dependencies]
# RP2040 HAL (Hardware Abstraction Layer)
rp2040-hal = { version = "0.10", features = ["rt", "critical-section-impl"] }

# Board support package for Raspberry Pi Pico pinout
rp-pico = "0.9"

# Cortex-M runtime and support
cortex-m = "0.7"
cortex-m-rt = "0.7"

# Panic handler: halt on panic (required for no_std)
panic-halt = "1.0"

# defmt logging framework (lightweight, no format strings on target)
defmt = "0.3"
defmt-rtt = "0.4"

# Embedded HAL traits
embedded-hal = "1.0"

[profile.dev]
codegen-units = 1
debug = 2
debug-assertions = true
incremental = false
opt-level = "s"
overflow-checks = true

[profile.release]
codegen-units = 1
debug = 2
debug-assertions = false
incremental = false
lto = "fat"
opt-level = "s"
overflow-checks = false
```

### Understanding the Dependencies

| Crate | Role |
|-------|------|
| `rp2040-hal` | The HAL (hardware abstraction layer): functions for the RP2040 peripherals (GPIO, timers, PWM, I2C, SPI). Each peripheral and pin has its own type, and that is how the compiler can check how you use it |
| `rp-pico` | Names the pins of the Pico board (`pins.led` is GP25) |
| `cortex-m` | Access to the ARM core itself (interrupt control, core registers). The `rp2040-hal` already provides the critical-section implementation, so do not add `critical-section-single-core` here |
| `cortex-m-rt` | The startup code: vector table, stack pointer, then a call to your `main()` |
| `panic-halt` | A panic is Rust's controlled stop when the program meets an error it cannot continue from. This crate decides what a panic does: stop the CPU (`panic-probe` prints the reason first) |
| `defmt` | Logging that keeps the text of each message on your computer and sends only a small number from the chip (saves flash) |
| `defmt-rtt` | Carries the defmt data to the debug probe over RTT |
| `embedded-hal` | Traits for peripherals. A trait is a named set of functions that a type promises to have, like an interface: `OutputPin` promises `set_high()` and `set_low()` |

### memory.x

The linker is the tool that gives every function and variable its final address, so it must know where the chip's memory is. A C project for the Pico takes this file from the SDK. Here you write it:

```ld
MEMORY {
    BOOT2 : ORIGIN = 0x10000000, LENGTH = 0x100
    FLASH : ORIGIN = 0x10000100, LENGTH = 2048K - 0x100
    RAM   : ORIGIN = 0x20000000, LENGTH = 256K
}

EXTERN(BOOT2_FIRMWARE)

SECTIONS {
    .boot2 ORIGIN(BOOT2) :
    {
        KEEP(*(.boot2));
    } > BOOT2
} INSERT BEFORE .text;
```

The file declares three regions:

- `BOOT2` is the first 256 bytes of flash (`0x100`). The RP2040 has no flash inside the chip. It runs code from a separate flash chip on the board, and a small second-stage bootloader in these 256 bytes sets that chip up. The `rp-pico` crate supplies the bootloader (from the `rp2040-boot2` crate).
- `FLASH` is the rest of the 2 MB, from `0x10000100`: your code and constant data.
- `RAM` is 256 KB from `0x20000000`: the stack and the variables. The RP2040 has 264 KB of RAM in all; this file uses the main block of 256 KB.

### .cargo/config.toml

Create `.cargo/config.toml` to set the default build target and linker:

```toml
[target.thumbv6m-none-eabi]
runner = "probe-rs run --chip RP2040"

rustflags = [
    "-C", "linker=flip-link",
    "-C", "link-arg=--nmagic",
    "-C", "link-arg=-Tlink.x",
    "-C", "link-arg=-Tdefmt.x",
]

[build]
target = "thumbv6m-none-eabi"

[env]
DEFMT_LOG = "debug"
```

What each setting does:

- `target`: every `cargo build` cross-compiles for the Cortex-M0+, so you do not type `--target` each time.
- `runner`: `cargo run` loads the program into the Pico and shows the RTT log lines.
- `linker=flip-link`: links through the wrapper that protects your variables from a stack overflow.
- `-Tlink.x`: the linker script from cortex-m-rt that places the vector table and the memory sections.
- `-Tdefmt.x`: the linker script from defmt for its table of message texts.
- `DEFMT_LOG`: the lowest log level that is kept (trace, debug, info, warn, error).

### build.rs

Cargo runs `build.rs` on your computer before it compiles the project. This one copies `memory.x` to the folder where the linker looks for it:

```rust
use std::env;
use std::fs::File;
use std::io::Write;
use std::path::PathBuf;

fn main() {
    let out = &PathBuf::from(env::var_os("OUT_DIR").unwrap());

    File::create(out.join("memory.x"))
        .unwrap()
        .write_all(include_bytes!("memory.x"))
        .unwrap();

    println!("cargo:rustc-link-search={}", out.display());
    println!("cargo:rerun-if-changed=memory.x");
}
```

## Writing the Blink Program

<InArticleAd />


### src/main.rs

```rust
//! Blinking LED with defmt RTT logging on the Raspberry Pi Pico.
//!
//! Toggles the onboard LED (GP25) and an external LED (GP15) at 1 Hz.
//! Prints the LED state and cycle count over RTT using defmt.

#![no_std]
#![no_main]

use panic_halt as _;
use defmt_rtt as _;

use rp_pico::entry;
use rp_pico::hal;
use rp_pico::hal::pac;
use rp_pico::hal::Clock;

use embedded_hal::digital::OutputPin;
use embedded_hal::delay::DelayNs;

/// Entry point. The `#[entry]` macro from cortex-m-rt ensures this
/// function is called after the runtime initializes the stack and
/// copies .data/.bss sections.
#[entry]
fn main() -> ! {
    defmt::info!("Booting rp2040-blink");

    // ---- Peripheral access ----
    // Take the singleton peripheral access crate (PAC) instance.
    // This can only be called once; calling it again would panic.
    let mut pac = pac::Peripherals::take().unwrap();

    // Set up the watchdog driver (needed for clock configuration)
    let mut watchdog = hal::Watchdog::new(pac.WATCHDOG);

    // Configure clocks: 125 MHz system clock from the crystal oscillator
    let clocks = hal::clocks::init_clocks_and_plls(
        rp_pico::XOSC_CRYSTAL_FREQ,
        pac.XOSC,
        pac.CLOCKS,
        pac.PLL_SYS,
        pac.PLL_USB,
        &mut pac.RESETS,
        &mut watchdog,
    )
    .ok()
    .unwrap();

    defmt::info!(
        "System clock: {} MHz",
        clocks.system_clock.freq().to_MHz()
    );

    // ---- Timer for delays ----
    let mut timer = rp_pico::hal::Timer::new(
        pac.TIMER,
        &mut pac.RESETS,
        &clocks,
    );

    // ---- GPIO setup ----
    let sio = hal::Sio::new(pac.SIO);
    let pins = rp_pico::Pins::new(
        pac.IO_BANK0,
        pac.PADS_BANK0,
        sio.gpio_bank0,
        &mut pac.RESETS,
    );

    // Onboard LED on GP25
    let mut led_onboard = pins.led.into_push_pull_output();

    // External LED on GP15
    let mut led_external = pins.gpio15.into_push_pull_output();

    defmt::info!("GPIO configured. Starting blink loop.");

    // ---- Main loop ----
    let mut cycle: u32 = 0;

    loop {
        // Turn LEDs on
        led_onboard.set_high().unwrap();
        led_external.set_high().unwrap();
        defmt::info!("Cycle {}: LEDs ON", cycle);

        // Delay 500 ms
        timer.delay_ms(500);

        // Turn LEDs off
        led_onboard.set_low().unwrap();
        led_external.set_low().unwrap();
        defmt::info!("Cycle {}: LEDs OFF", cycle);

        // Delay 500 ms
        timer.delay_ms(500);

        cycle = cycle.wrapping_add(1);
    }
}
```

### Line-by-Line Walkthrough

**`#![no_std]`** tells the compiler not to link the standard library, which needs an operating system (files, a network, a heap). You still have `core`: the basic types, including `Option` and `Result`, which appear below.

**`#![no_main]`** says that the program supplies its own entry point. The `#[entry]` attribute from `cortex-m-rt` generates the real one, which sets the stack pointer and then calls our function.

**`fn main() -> !`**: the `!` means this function never returns. There is no operating system to return to.

**`let` and `let mut`**: a variable cannot change unless it is declared with `mut`. This is the reverse of C, where you add `const` to forbid a change.

**`pac::Peripherals::take().unwrap()`**: in C, any file can write to any peripheral register, so two modules can configure the same peripheral differently and neither knows. Rust closes this door with ownership: a value has one owner, and only the owner can use it. `take()` gives you the one value that stands for all the peripheral registers. It returns an `Option`, which is either `Some(peripherals)` or `None`. Think of a C pointer that may be NULL, with one difference: the compiler does not let you reach the contents until you say what happens for `None`. The first call returns `Some`, and every later call returns `None`. Here `.unwrap()` says "I am sure it is `Some`; panic if it is not".

**`pins.led.into_push_pull_output()`**: in C, `gpio_put()` on a pin that was never made an output compiles and does nothing. Here the configuration of a pin is part of its type. `pins.led` starts as an unconfigured pin. `into_push_pull_output()` takes that value and gives back a new value of a different type, an output pin, and only that type has `set_high()`. The old `pins.led` cannot be used again. This is the typestate pattern: the state of the hardware is written in the type, so the compiler can refuse a wrong use.

**`set_high().unwrap()`**: `set_high()` returns a `Result`, which is `Ok` if the operation worked and `Err` with a reason if it did not. It is a C error code that the compiler does not let you ignore without saying so. A GPIO write on the RP2040 cannot fail, but the `OutputPin` trait also serves chips where it can (a pin on an I2C port expander), so the return type stays. `unwrap()` takes the `Ok` and panics on an `Err`.

## C vs Rust: What is Different?

<InArticleAd />


<Tabs>
<TabItem label="C Blink (Pico SDK)">
```c
#include "pico/stdlib.h"

int main() {
    const uint LED_PIN = 25;
    gpio_init(LED_PIN);
    gpio_set_dir(LED_PIN, GPIO_OUT);

    while (true) {
        gpio_put(LED_PIN, 1);
        sleep_ms(500);
        gpio_put(LED_PIN, 0);
        sleep_ms(500);
    }
}
```

**What C does not catch:**
- Nothing prevents calling `gpio_put()` before `gpio_init()`
- Nothing prevents calling `gpio_put()` with an invalid pin number (e.g., pin 99)
- Nothing prevents two modules from calling `gpio_init()` on the same pin
- `gpio_set_dir()` could be called with an incorrect direction and the compiler would not notice
</TabItem>
<TabItem label="Rust Blink (rp2040-hal)">
```rust
let pins = rp_pico::Pins::new(/* ... */);
let mut led = pins.led.into_push_pull_output();

loop {
    led.set_high().unwrap();
    timer.delay_ms(500);
    led.set_low().unwrap();
    timer.delay_ms(500);
}
```

**What Rust catches at compile time:**
- `into_push_pull_output()` consumes the pin; you cannot configure it twice
- `set_high()` only exists on output pin types; calling it on an input pin is a type error
- Pin numbers are type-checked; there is no `gpio_put(99, 1)` equivalent
- The peripheral singleton ensures `Pins::new()` can only be called once
</TabItem>
</Tabs>

In C these mistakes compile, and you find them in testing or in the field. In Rust they do not compile. A compiler error costs a minute at your desk. The same mistake in a delivered product costs a visit to the site.

## defmt: Structured Logging for Embedded

<InArticleAd />


defmt (deferred formatting) is a logging library for small chips. `printf` stores every format string in the chip's flash and builds the text on the chip. defmt puts only a small index for each message on the chip. The text stays in the ELF file on your computer, and probe-rs joins the two. The program uses less flash, and a log call takes less time.

| Feature | printf (C) | defmt (Rust) |
|---------|-----------|-------------|
| Structured data | No | Yes (derives, custom types) |
| Log levels | Manual | Built-in (trace, debug, info, warn, error) |
| Transport | Typically UART | RTT (through debug probe, zero pins used) |

### defmt Log Levels

```rust
defmt::trace!("very detailed, usually disabled");
defmt::debug!("development-time debugging info");
defmt::info!("normal operational messages");
defmt::warn!("something unexpected but recoverable");
defmt::error!("something went wrong");
```

Set the minimum level in `.cargo/config.toml` with `DEFMT_LOG = "info"` to suppress trace and debug messages in release builds.

### Logging Custom Types

```rust
#[derive(defmt::Format)]
struct SensorReading {
    temperature_c: i16,
    humidity_pct: u8,
}

let reading = SensorReading {
    temperature_c: 23,
    humidity_pct: 55,
};
defmt::info!("Sensor: {}", reading);
// Output: Sensor: SensorReading { temperature_c: 23, humidity_pct: 55 }
```

After a build, two entries are new. `target/` holds everything the compiler produced, and the program itself is the last file in the tree. `Cargo.lock` records the exact version of every crate that was used. Cargo writes it; keep it in version control so that every build uses the same versions.

### How the Build Works

<Steps>
1. `cargo build` runs `build.rs` first, which copies `memory.x` to the folder where the linker looks for it.

2. Cargo then calls the compiler `rustc` with `--target thumbv6m-none-eabi`, so it produces code for the Cortex-M0+.

3. The linker (`flip-link`, which wraps `rust-lld`) joins your code with the startup code of `cortex-m-rt`, places the sections as `memory.x` and `link.x` say, and writes an ELF file.

4. `cargo run` passes the ELF file to `probe-rs run`, which loads it into the Pico over SWD and resets the chip.

5. RTT starts. probe-rs reads the defmt data from a RAM buffer through the debug probe and turns it into text on your computer, with the message texts stored in the ELF file (in its `.defmt` section, which is not loaded into the chip).
</Steps>

## Production Notes

<InArticleAd />


<Card title="Production Considerations" icon="setting">

**Flash protection:** The RP2040 has no read-out protection of the kind an STM32 has. Anyone with the board can read your firmware from the flash chip. For a commercial product, consider encrypted firmware and a signed boot flow.

**Panic behavior:** `panic-halt` loops forever and says nothing. During development, use `panic-probe`, which prints the panic message over defmt and then stops. For delivered firmware, use `panic-reset`, which restarts the chip.

**Binary size:** The setting `opt-level = "s"` optimizes for size, and `opt-level = "z"` goes further.

**Watchdog timer:** Delivered firmware should enable the watchdog timer, which restarts a program that hangs. The rp2040-hal `Watchdog` driver supports this.

**Why flip-link:** On Cortex-M the stack normally starts at the top of RAM and grows down toward the variables at the bottom. If it grows too far, it overwrites them and nothing reports it. With the stack at the bottom, an overflow leaves RAM, and the HardFault tells you what happened.
