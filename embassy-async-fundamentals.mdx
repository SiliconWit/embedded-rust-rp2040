A device that blinks a light, watches a button and sends a report has three slow jobs, and each job is mostly waiting. In C you write one large loop, where one long delay makes the button feel dead, or you add an RTOS and give every task its own stack, whose size you must guess. Embassy is a third way. You write each job as a function that looks sequential, and at every place where the job must wait it gives the processor back, so another job can run. All jobs share one stack and there is no heap. In this lesson you build three such tasks on a Raspberry Pi Pico: an LED blinker, a button monitor and a reporter. #Embassy #AsyncEmbedded #RP2040

## Why Embassy, Not an RTOS

<InArticleAd />

Most of what a microcontroller does is waiting: for a timer, for a button, for a byte from a sensor. The question is what the processor does during a wait, and what it costs in memory to have several waits open at once.

An RTOS (real-time operating system, for example FreeRTOS or Zephyr) answers with one stack per task. A stack is the memory where a function keeps its local variables. The scheduler may stop a task between any two instructions and continue another (this is preemption), so each task needs a private stack that is large enough for its worst case. This works, but it costs RAM: 512 to 2048 bytes of stack for each task, and a kernel heap of 4 KB or more. Three FreeRTOS tasks take 8 to 10 KB.

Embassy answers in another way. Five words carry the whole idea, and every program from here on uses them:

- An `async fn` is a function that may stop in the middle and continue later. Calling it does not run it. The call returns a future.
- A future is a value that stands for work that is not finished yet: "500 ms have passed", "a byte has arrived".
- `.await` says: "I cannot continue until this future is finished, so give the processor to someone else." It is the only place where a task lets go of the processor.
- A task is an `async fn` that the program has started and that lives for the whole run.
- The executor is the small loop that owns the processor. To poll a task is to run it until its next `.await`. The executor polls each task that is ready, and when no task is ready it puts the processor to sleep.

Think of one cook with three pots, who stirs a pot, sets a timer for it and moves to the next. The comparison stops at one point: a cook who sees a pot boil over can jump to it, but the executor cannot take the processor from a task. It must wait for that task's next `.await`.

The memory saving comes from the compiler. It turns each `async fn` into a state machine: a small struct that remembers at which `.await` the task stopped, and only the local variables it still needs after that point. The size of that struct is known at build time, so no task needs a stack of its own.

The drawing shows the three tasks of this lesson for two seconds. The button is pressed at 1100 ms and released at 1300 ms.

```text
 time (ms)  0         500       1000      1500      2000
            |         |         |         |         |
 blinker    █.........█.........█.........█.........█
 button     █.....................█...█..............
 reporter   █..........................█.............
 processor  █zzzzzzzzz█zzzzzzzzz█z█zzz██zz█zzzzzzzzz█

 █  a task runs for some microseconds, to its next .await
 .  the task waits at an .await and uses no processor time
 z  no task is ready, so the processor sleeps
```

Each task runs only for a moment and then waits. After the release the button task sends a message, and the reporter runs just after it, not at the same time: only one task runs at any moment.

### The Key Differences

<CardGrid>
  <Card title="No preemption" icon="warning">
    A task runs until it reaches an `.await`. If a task never awaits, no other task runs at all: the LED stops and the button is dead. In return, a task is never cut in the middle of an update, so the data races that preemption causes cannot happen.
  </Card>
  <Card title="No stacks to size, no heap" icon="approve-check">
    In FreeRTOS you guess the deepest stack use of each task: too low overflows, too high wastes RAM. In Embassy the compiler calculates the size of each state machine, and nothing calls `malloc`, so the linker shows the whole memory use.
  </Card>
  <Card title="Checked at compile time" icon="approve-check">
    The compiler warns you when you forget to `.await` a future. It refuses a program in which two tasks change the same data without a lock, or use the same peripheral.
  </Card>
</CardGrid>

## Your First Async Blink

<InArticleAd />

The smallest Embassy program is one async task that blinks an LED. Every Embassy application has this structure.

```rust
// src/main.rs - Minimal async blink
#![no_std]
#![no_main]

use embassy_executor::Spawner;
use embassy_rp::gpio::{Level, Output};
use embassy_time::Timer;
use {defmt_rtt as _, panic_halt as _};

#[embassy_executor::main]
async fn main(_spawner: Spawner) {
    // Initialize all RP2040 peripherals
    let p = embassy_rp::init(Default::default());

    // Configure GP15 as a push-pull output, initially low
    let mut led = Output::new(p.PIN_15, Level::Low);

    loop {
        led.set_high();
        Timer::after_millis(500).await;
        led.set_low();
        Timer::after_millis(500).await;
    }
}
```

Four lines need an explanation.

`#![no_std]` and `#![no_main]`: this is a bare-metal program. There is no standard library and no ordinary `fn main()`. The Embassy macro does the startup.

`#[embassy_executor::main]`: this macro creates the executor and makes `async fn main` the first task. From then on the executor polls a task each time an interrupt marks it as ready.

`embassy_rp::init(Default::default())`: this call sets up the clocks and returns a `Peripherals` struct. Every hardware resource (each pin, each SPI block, each timer) is one field of it, and you can move a field into one task only.

`Timer::after_millis(500).await`: `Timer::after_millis(500)` makes a future that finishes after 500 ms, and `.await` gives the processor back until then. Here there is no other task, so the executor puts the processor to sleep until the timer interrupt.

## Spawning Multiple Tasks

<InArticleAd />

To spawn a task is to hand it to the executor, so that it starts to run beside the others. A task is an `async fn` marked with `#[embassy_executor::task]`.

```rust
#![no_std]
#![no_main]

use embassy_executor::Spawner;
use embassy_rp::gpio::{Level, Output};
use embassy_time::Timer;
use {defmt_rtt as _, panic_halt as _};

#[embassy_executor::task]
async fn blink_fast(mut led: Output<'static>) {
    loop {
        led.toggle();
        Timer::after_millis(100).await;
    }
}

#[embassy_executor::task]
async fn blink_slow(mut led: Output<'static>) {
    loop {
        led.toggle();
        Timer::after_millis(1000).await;
    }
}

#[embassy_executor::main]
async fn main(spawner: Spawner) {
    let p = embassy_rp::init(Default::default());

    let led1 = Output::new(p.PIN_15, Level::Low);
    let led2 = Output::new(p.PIN_16, Level::Low);

    // Spawn both tasks. They run concurrently.
    spawner.spawn(blink_fast(led1)).unwrap();
    spawner.spawn(blink_slow(led2)).unwrap();

    // Main task has nothing left to do, but the executor keeps running
    // the spawned tasks. We can await forever here.
    loop {
        Timer::after_secs(3600).await;
    }
}
```

`Output::new(p.PIN_15, Level::Low)` takes ownership of `p.PIN_15`. If you pass the same pin to both tasks, the compiler stops with "use of moved value". In C, two FreeRTOS tasks can write to the same GPIO register with no warning.

The type `Output<'static>` contains a new word. `'static` is a lifetime that means "valid for the whole run of the program". A spawned task may run at any later time and may never end, so everything it holds must stay valid for ever. A pin meets this, because it exists as long as the chip has power. A reference to a local variable of `main` does not.

### How the Executor Schedules Tasks

<Steps>
1. All spawned tasks are polled once at startup.

2. Each task runs until it reaches an `.await` on a future that is not finished (such as `Timer::after_millis`).

3. The future leaves a waker with the timer. A waker is a small handle that means "mark this task as ready".

4. When every task is waiting, the executor puts the processor to sleep with WFE (wait for event), an instruction that sleeps until an interrupt arrives.

5. The timer interrupt fires, and its handler uses the waker to mark the task as ready.

6. The executor wakes and polls only the tasks that are ready.

7. Return to step 2.
</Steps>

Note what step 5 does not do: the interrupt marks the task, it does not run the task. If another task holds the processor at that moment, the ready task waits until that one reaches an `.await`. So the price of having no preemption is one rule: never run for long without an `.await`. A loop that calculates for 100 ms makes every other task up to 100 ms late.

## Embassy Time: Delays, Timeouts, and Tickers

<InArticleAd />

The `embassy-time` crate holds everything that has to do with time. `cortex_m::delay::Delay` counts in a loop and keeps the processor. An Embassy timer is driven by an interrupt, so other tasks run during the wait.

### Basic Delays

```rust
use embassy_time::Timer;

// Wait for a fixed duration
Timer::after_millis(250).await;
Timer::after_secs(2).await;
Timer::after_micros(100).await;
```

### Timeouts

A wait with no limit is a risk: a sensor that never answers stops its task for ever. `with_timeout` puts a limit on any future. If the future is not finished in time, `with_timeout` returns an error and the task continues.

```rust
use embassy_time::{Timer, Duration, with_timeout};

// Wait for a button press, but give up after 5 seconds
match with_timeout(Duration::from_secs(5), wait_for_button_press()).await {
    Ok(()) => {
        defmt::info!("Button pressed within timeout");
    }
    Err(_) => {
        defmt::info!("Timeout: no button press detected");
    }
}
```

### Tickers for Periodic Tasks

A loop that works for 30 ms and then waits 100 ms repeats every 130 ms, not every 100 ms, and the error adds up. A `Ticker` fires at fixed moments, so the time your task spends working is taken out of the wait.

```rust
use embassy_time::{Duration, Ticker};

#[embassy_executor::task]
async fn sensor_reader() {
    // Tick every 100 ms, regardless of how long processing takes
    let mut ticker = Ticker::every(Duration::from_millis(100));

    loop {
        // Read sensor, process data...
        let value = read_sensor().await;
        process(value);

        // Wait for the next tick. If processing took 30 ms,
        // this waits only 70 ms more.
        ticker.next().await;
    }
}
```

### Instant for Measuring Elapsed Time

```rust
use embassy_time::Instant;

let start = Instant::now();
// ... do some work ...
let elapsed = start.elapsed();
defmt::info!("Operation took {} ms", elapsed.as_millis());
```

## Inter-Task Communication: Channels

<InArticleAd />

Two tasks cannot both write one variable freely, and Rust does not let them try. The usual way to pass data is a channel: a queue with a fixed number of places. One task puts messages in and another takes them out in the same order (FIFO, first in, first out). If the queue is full, `send(...).await` waits for a free place. If it is empty, `receive().await` waits for a message. Other tasks run during both waits.

The channel is declared `static`. A `static` is a variable that is made once, at a fixed address, and exists for the whole run. That is how two tasks can both reach it, and why it needs no heap.

```rust
use embassy_sync::channel::Channel;
use embassy_sync::blocking_mutex::raw::CriticalSectionRawMutex;

// A channel that holds up to 4 ButtonEvent values
// The CriticalSectionRawMutex is the synchronization primitive for single-core use
static BUTTON_CHANNEL: Channel<CriticalSectionRawMutex, ButtonEvent, 4> = Channel::new();

#[derive(Clone, Copy)]
enum ButtonEvent {
    ShortPress,
    LongPress,
}

#[embassy_executor::task]
async fn button_task() {
    loop {
        let event = detect_button_event().await;
        BUTTON_CHANNEL.send(event).await;
    }
}

#[embassy_executor::task]
async fn led_task() {
    loop {
        // This awaits until a message arrives
        let event = BUTTON_CHANNEL.receive().await;
        match event {
            ButtonEvent::ShortPress => { /* toggle LED */ }
            ButtonEvent::LongPress => { /* change pattern */ }
        }
    }
}
```

The `4` in `Channel<..., 4>` is the number of places, fixed at compile time. `CriticalSectionRawMutex` names how the channel protects its inside: it turns interrupts off for the few instructions of each access. Several tasks may send to one channel. Several may receive, but each message goes to only one of them.

## Inter-Task Communication: Signals

<InArticleAd />

A `Signal` is simpler than a channel: it holds one value. If the sender signals three times before the receiver looks, the receiver gets only the last value. Use a signal for "what is the state now", where an old value is worth nothing. Use a channel when every message counts.

```rust
use embassy_sync::signal::Signal;
use embassy_sync::blocking_mutex::raw::CriticalSectionRawMutex;

static PATTERN_SIGNAL: Signal<CriticalSectionRawMutex, BlinkPattern> = Signal::new();

#[derive(Clone, Copy)]
enum BlinkPattern {
    Slow,
    Fast,
    Sos,
}

// From the button task:
PATTERN_SIGNAL.signal(BlinkPattern::Fast);

// From the LED task:
let pattern = PATTERN_SIGNAL.wait().await;
```

## RAM Comparison: Embassy vs FreeRTOS

<InArticleAd />

The Tweede Golf embedded systems consultancy published benchmarks comparing Embassy to FreeRTOS on the same hardware (an STM32F446 at 180 MHz, in 2022; expect similar ratios, not the same numbers, on the RP2040). Their findings:

| Metric | FreeRTOS | Embassy | Ratio |
|--------|----------|---------|-------|
| Program size (flash) | 20,676 bytes | 14,272 bytes | Embassy is 69% |
| Static memory (RAM) | 5,480 bytes | 872 bytes | Embassy is 16% |
| Interrupt time (average) | 2.962 us | 1.450 us | Embassy is 2.0x faster |
| Thread time (average) | 16.19 us | 11.64 us | Embassy is 1.4x faster |
| Interrupt latency (average) | 4.973 us | 3.738 us | Embassy is 1.3x faster |

The RAM saving comes from the missing per-task stacks. On an RP2040 with 264 KB of SRAM this matters little for 3 tasks. With 10 or 20 tasks, FreeRTOS can use more than 40 KB for stacks alone, while Embassy stays under 5 KB, and the difference is free for buffers and sensor data.

## C vs Rust: FreeRTOS Task vs Embassy Async Task

<InArticleAd />

<Tabs>
<TabItem label="C (FreeRTOS)">

```c
// FreeRTOS task: LED blinker
// Must pre-allocate a stack for this task.
// Stack overflow = silent corruption or hard fault.

#include "FreeRTOS.h"
#include "task.h"
#include "hardware/gpio.h"

#define LED_PIN 15
#define STACK_SIZE 256  // words (1024 bytes) - is this enough? Too much?

void blink_task(void *params) {
    gpio_init(LED_PIN);
    gpio_set_dir(LED_PIN, GPIO_OUT);

    for (;;) {
        gpio_put(LED_PIN, 1);
        vTaskDelay(pdMS_TO_TICKS(500));
        gpio_put(LED_PIN, 0);
        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void app_main(void) {
    // Stack size is a guess. Too small = stack overflow.
    // Too large = wasted RAM. No compile-time check.
    xTaskCreate(
        blink_task,
        "blink",
        STACK_SIZE,     // 1024 bytes allocated, maybe 200 used
        NULL,
        1,              // Priority
        NULL
    );

    // Another task: another stack allocation guess
    xTaskCreate(
        button_task,
        "button",
        STACK_SIZE,     // Another 1024 bytes
        NULL,
        2,
        NULL
    );

    vTaskStartScheduler();
}

// Total RAM for 2 tasks: ~2048 bytes stacks + 184 bytes TCBs
// + FreeRTOS heap overhead
// Nothing prevents both tasks from writing to LED_PIN simultaneously
```

</TabItem>
<TabItem label="Rust (Embassy)">

```rust
// Embassy async task: LED blinker
// No stack allocation. The compiler calculates the exact
// state machine size. Pin ownership prevents conflicts.

#![no_std]
#![no_main]

use embassy_executor::Spawner;
use embassy_rp::gpio::{Level, Output};
use embassy_time::Timer;
use {defmt_rtt as _, panic_halt as _};

#[embassy_executor::task]
async fn blink_task(mut led: Output<'static>) {
    // The LED pin is moved into this task.
    // No other task can access it. Compile-time guarantee.
    loop {
        led.set_high();
        Timer::after_millis(500).await;
        // At this .await, the state machine stores only: led, and
        // which branch of the loop we are in. Total: ~16 bytes.
        led.set_low();
        Timer::after_millis(500).await;
    }
}

#[embassy_executor::main]
async fn main(spawner: Spawner) {
    let p = embassy_rp::init(Default::default());

    let led = Output::new(p.PIN_15, Level::Low);
    // p.PIN_15 is consumed. Cannot be used again.

    spawner.spawn(blink_task(led)).unwrap();
    // Attempting spawner.spawn(other_task(led)) here
    // would fail at compile time: "use of moved value: led"

    loop {
        Timer::after_secs(3600).await;
    }
}

// Total RAM for 2 tasks: ~32 bytes of state machines
// + shared main stack (~2 KB, used by all tasks sequentially)
// Pin conflicts are impossible. There are no per-task stacks to size.
```

</TabItem>
</Tabs>

In the C version you guess the stack sizes and keep two tasks away from one pin by discipline. In the Rust version the compiler does both, and there is one stack to size, because an async task keeps nothing on the call stack while it waits.

## Complete Project: Multi-Task System

<InArticleAd />

The project has three tasks. They pass data through one channel and one signal.

### System Architecture

```text
 ┌────────────────┐   channel    ┌─────────────────┐
 │  Button task   ├─────────────>│  Reporter task  │
 │  (GP14 input)  │ ButtonEvent  │  (log output)   │
 └───────┬────────┘              └─────────────────┘
         │ signal
         │ BlinkPattern
         v
 ┌────────────────┐
 │  Blinker task  │
 │  (GP15 LED)    │
 └────────────────┘
```

The button task measures how long the button is held. Every press sends a `ButtonEvent` through the channel to the reporter task, because no press may be lost. A long press also sends the next `BlinkPattern` through the signal to the blinker task, which needs only the newest pattern.

### Full Source Code

```rust
// src/main.rs
// Multi-task Embassy system: blinker + button monitor + serial reporter

#![no_std]
#![no_main]

use embassy_executor::Spawner;
use embassy_rp::gpio::{Input, Level, Output, Pull};
use embassy_sync::blocking_mutex::raw::CriticalSectionRawMutex;
use embassy_sync::channel::Channel;
use embassy_sync::signal::Signal;
use embassy_time::{Duration, Instant, Timer};
use {defmt_rtt as _, panic_halt as _};

// -----------------------------------------------------------
// Pin Assignments
// -----------------------------------------------------------
// GP15: External LED (through 220 ohm resistor)
// GP14: Push button (active-low, internal pull-up)

// -----------------------------------------------------------
// Shared Communication Primitives (statically allocated)
// -----------------------------------------------------------

/// Channel for button events: button task -> reporter task
static BUTTON_CHANNEL: Channel<CriticalSectionRawMutex, ButtonEvent, 8> = Channel::new();

/// Signal for blink pattern changes: button task -> blinker task
static PATTERN_SIGNAL: Signal<CriticalSectionRawMutex, BlinkPattern> = Signal::new();

// -----------------------------------------------------------
// Data Types
// -----------------------------------------------------------

#[derive(Clone, Copy, defmt::Format)]
enum ButtonEvent {
    ShortPress,
    LongPress,
}

#[derive(Clone, Copy, PartialEq, defmt::Format)]
enum BlinkPattern {
    Slow,       // 1 Hz: 500 ms on, 500 ms off
    Fast,       // 5 Hz: 100 ms on, 100 ms off
    Heartbeat,  // Double-pulse like a heartbeat
}

impl BlinkPattern {
    /// Cycle to the next pattern
    fn next(self) -> Self {
        match self {
            BlinkPattern::Slow => BlinkPattern::Fast,
            BlinkPattern::Fast => BlinkPattern::Heartbeat,
            BlinkPattern::Heartbeat => BlinkPattern::Slow,
        }
    }
}

// -----------------------------------------------------------
// Task 1: LED Blinker
// -----------------------------------------------------------

#[embassy_executor::task]
async fn blinker_task(mut led: Output<'static>) {
    let mut pattern = BlinkPattern::Slow;

    loop {
        // Check if a new pattern has been signaled (non-blocking check)
        if let Some(new_pattern) = PATTERN_SIGNAL.try_take() {
            pattern = new_pattern;
            defmt::info!("Blinker: pattern changed to {:?}", pattern);
        }

        // Execute one cycle of the current pattern
        match pattern {
            BlinkPattern::Slow => {
                led.set_high();
                Timer::after_millis(500).await;
                led.set_low();
                Timer::after_millis(500).await;
            }
            BlinkPattern::Fast => {
                led.set_high();
                Timer::after_millis(100).await;
                led.set_low();
                Timer::after_millis(100).await;
            }
            BlinkPattern::Heartbeat => {
                // First pulse
                led.set_high();
                Timer::after_millis(100).await;
                led.set_low();
                Timer::after_millis(100).await;
                // Second pulse
                led.set_high();
                Timer::after_millis(100).await;
                led.set_low();
                // Pause before next heartbeat
                Timer::after_millis(700).await;
            }
        }
    }
}

// -----------------------------------------------------------
// Task 2: Button Monitor with Debounce
// -----------------------------------------------------------

#[embassy_executor::task]
async fn button_task(mut button: Input<'static>) {
    let mut press_count: u32 = 0;
    let mut pattern = BlinkPattern::Slow; // The pattern the blinker is using

    loop {
        // Wait for button press (falling edge, since active-low)
        button.wait_for_falling_edge().await;

        // Debounce: wait 20 ms and check if still pressed
        Timer::after_millis(20).await;
        if button.is_high() {
            continue; // Bounce, not a real press
        }

        // Button is pressed. Measure how long it stays pressed.
        let press_start = Instant::now();

        // Wait for release (rising edge)
        button.wait_for_rising_edge().await;

        // Debounce the release
        Timer::after_millis(20).await;

        let press_duration = press_start.elapsed();

        if press_duration.as_millis() > 1000 {
            // Long press: change blink pattern
            press_count += 1;
            let next = pattern.next();
            pattern = next;
            PATTERN_SIGNAL.signal(next);
            BUTTON_CHANNEL.send(ButtonEvent::LongPress).await;
            defmt::info!(
                "Button: long press ({} ms), pattern -> {:?}",
                press_duration.as_millis(),
                next
            );
        } else {
            // Short press: just report
            press_count += 1;
            BUTTON_CHANNEL.send(ButtonEvent::ShortPress).await;
            defmt::info!(
                "Button: short press ({} ms), total presses: {}",
                press_duration.as_millis(),
                press_count
            );
        }
    }
}

// -----------------------------------------------------------
// Task 3: Serial Reporter
// -----------------------------------------------------------

#[embassy_executor::task]
async fn reporter_task() {
    let boot_time = Instant::now();
    let mut total_short: u32 = 0;
    let mut total_long: u32 = 0;

    loop {
        // Try to receive a button event with a 2-second timeout.
        // If no event arrives, we still print a status report.
        match embassy_time::with_timeout(
            Duration::from_secs(2),
            BUTTON_CHANNEL.receive(),
        )
        .await
        {
            Ok(ButtonEvent::ShortPress) => {
                total_short += 1;
                defmt::info!("Reporter: short press received (total: {})", total_short);
            }
            Ok(ButtonEvent::LongPress) => {
                total_long += 1;
                defmt::info!("Reporter: long press received (total: {})", total_long);
            }
            Err(_) => {
                // Timeout: no button event in 2 seconds. Print status.
            }
        }

        // Periodic status report
        let uptime_secs = boot_time.elapsed().as_secs();
        defmt::info!(
            "Status: uptime={}s, short_presses={}, long_presses={}, total={}",
            uptime_secs,
            total_short,
            total_long,
            total_short + total_long
        );
    }
}

// -----------------------------------------------------------
// Main: Initialize and Spawn Tasks
// -----------------------------------------------------------

#[embassy_executor::main]
async fn main(spawner: Spawner) {
    let p = embassy_rp::init(Default::default());

    // Configure peripherals
    let led = Output::new(p.PIN_15, Level::Low);
    let button = Input::new(p.PIN_14, Pull::Up);

    defmt::info!("Embassy multi-task system starting");
    defmt::info!("Short press: report event");
    defmt::info!("Long press (>1s): change blink pattern");

    // Spawn all three tasks
    spawner.spawn(blinker_task(led)).unwrap();
    spawner.spawn(button_task(button)).unwrap();
    spawner.spawn(reporter_task()).unwrap();

    // Main task: idle forever. The executor runs the spawned tasks.
    // In a production system, you might use this task for
    // watchdog feeding or low-priority background work.
    loop {
        Timer::after_secs(3600).await;
    }
}
```

### How the Tasks Interact

Follow one typical run.

<Steps>
1. **Startup**: The executor polls all three tasks. Each runs until its first `.await`. The blinker starts its first `Timer::after_millis(500)`. The button task starts `wait_for_falling_edge()`. The reporter starts its `with_timeout(2s, receive())`. All three now wait, and the processor sleeps.

2. **500 ms later**: The timer interrupt fires. The blinker task runs, changes the LED, and starts the next `Timer::after_millis(500)`. The other two tasks stay asleep. Processor time used: microseconds.

3. **The user presses the button**: The GPIO interrupt fires on the falling edge. The button task waits 20 ms and reads the pin again, because a mechanical contact bounces for some milliseconds and one press must not count as several (this is debounce). Then it notes the time.

4. **The user releases after 200 ms (short press)**: The button task sends `ButtonEvent::ShortPress` through `BUTTON_CHANNEL`. This marks the reporter task as ready. The reporter runs when the button task reaches its next `.await`, adds one to its counter and prints the status.

5. **The user holds for 2 seconds (long press)**: The button task sends `BlinkPattern::Fast` through `PATTERN_SIGNAL` and `ButtonEvent::LongPress` through the channel. The blinker looks at the signal only at the start of a cycle, so the LED changes when the current cycle ends, up to one second later.

6. **No press for 2 seconds**: The reporter's `with_timeout` expires. It prints a status report (uptime, press counts) and waits again.
</Steps>

The `defmt::info!` lines of the project need a debug probe. For a board that stands alone you can add USB CDC, the USB class that makes the Pico appear as a serial port on your computer. The listing below shows the parts you add. It is a sketch, not a complete program.

use embassy_usb::UsbDevice;

bind_interrupts!(struct Irqs {
    USBCTRL_IRQ => UsbInterruptHandler<embassy_rp::peripherals::USB>;

#[embassy_executor::task]
async fn usb_task(mut device: UsbDevice<'static, Driver<'static, embassy_rp::peripherals::USB>>) {
    device.run().await;
}

#[embassy_executor::task]
async fn serial_reporter_task(
    mut class: CdcAcmClass<'static, Driver<'static, embassy_rp::peripherals::USB>>,

    // This is simplified for clarity
    "STATUS OK"

## Production Notes on Async Patterns

<InArticleAd />

### When to Use Channels vs Signals

| Use Case | Primitive | Reason |
|----------|-----------|--------|
| Button events that must not be lost | Channel | FIFO queue, every message is delivered |
| Current sensor reading | Signal | Only the latest value matters |
| Command queue from host to device | Channel | Commands must execute in order |
| Status flag (running/stopped) | Signal | Only current state matters |
| Data stream from ADC | Channel | Every sample must be processed |

### Avoiding Starvation

A task that never awaits stops all other tasks, and the compiler does not warn you. The usual form of the mistake, and its repair:

```rust
// BAD: This loop never awaits. All other tasks starve.
#[embassy_executor::task]
async fn compute_task() {
    loop {
        heavy_computation(); // Runs for 100 ms without yielding
    }
}

// GOOD: Yield periodically during long computations.
#[embassy_executor::task]
async fn compute_task() {
    loop {
        for chunk in data.chunks(64) {
            process_chunk(chunk);
            embassy_futures::yield_now().await; // Let other tasks run
        }
    }
}
```

### Static Allocation Only

Everything a task holds must be `'static`, so a task cannot borrow a local variable of `main`. You either move the data into the task, or you put it in a `static` variable, as the channel and the signal above. A `StaticCell` is a `static` place that is empty at first: you fill it once during the run, and it gives back a reference that is valid for ever.

```rust
// This will NOT compile:
#[embassy_executor::main]
async fn main(spawner: Spawner) {
    let mut buffer = [0u8; 256];
    spawner.spawn(my_task(&mut buffer)).unwrap();
    // error[E0597]: `buffer` does not live long enough
}

// This WILL compile: buffer is static
static BUFFER: StaticCell<[u8; 256]> = StaticCell::new();

#[embassy_executor::main]
async fn main(spawner: Spawner) {
    let buffer = BUFFER.init([0u8; 256]);
    spawner.spawn(my_task(buffer)).unwrap();
}
```

### Shared Mutable State with Mutex

When two tasks must read and write the same data, put it in a mutex, a lock that one task can hold at a time (`embassy_sync::mutex::Mutex`):

```rust
use embassy_sync::mutex::Mutex;
use embassy_sync::blocking_mutex::raw::CriticalSectionRawMutex;

static SHARED_STATE: Mutex<CriticalSectionRawMutex, SystemState> =
    Mutex::new(SystemState::new());

struct SystemState {
    press_count: u32,
    uptime_secs: u64,
    pattern: BlinkPattern,
}

impl SystemState {
    const fn new() -> Self {
        Self {
            press_count: 0,
            uptime_secs: 0,
            pattern: BlinkPattern::Slow,
        }
    }
}

#[embassy_executor::task]
async fn updater_task() {
    loop {
        {
            let mut state = SHARED_STATE.lock().await;
            state.press_count += 1;
        } // Lock is released when `state` goes out of scope

        Timer::after_secs(1).await;
    }
}

#[embassy_executor::task]
async fn reader_task() {
    loop {
        {
            let state = SHARED_STATE.lock().await;
            defmt::info!("Presses: {}", state.press_count);
        } // Lock released here

        Timer::after_secs(2).await;
    }
}
```

If a task asks for a mutex that another task holds, `lock().await` waits, and other tasks run during the wait. The lock is released when the guard (`state` above) goes out of scope, not at an `.await`. A task that awaits a timer while it holds the lock keeps every other user out for that whole time, so keep each locked block short, as shown. If a task needs two mutexes, always lock them in the same order. Otherwise two tasks can each hold one and wait for the other for ever (a deadlock).

## Summary

<InArticleAd />

An async task gives the processor back at every `.await`. The executor runs whichever task is ready and sleeps when none is. The compiler stores each task as a small state machine, so all tasks share one stack. A channel carries every message in order, a signal carries only the newest value, and both are `static`. The rule to remember: a task that never awaits stops all the others. Sensors and displays come next, in [I2C and SPI with embedded-hal](/education/embedded-rust-rp2040/i2c-spi-embedded-hal/).
